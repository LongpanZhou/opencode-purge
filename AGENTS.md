# Agent notes: catalog maintenance

This repository is an OpenCode V2 plugin. These instructions are for AI agents
asked to **update the persona catalog, run `update-md`, or fix a model that
resolves to the wrong (or no) prompt**. Follow them exactly; they describe the
system's actual behavior, not aspirational behavior.

## Mental model

```
upstream repo (GitHub)  ← personaRepoUrl, trusted source of prompt files
        │  autoPull: clone once → git pull --ff-only on start + interval
        ▼
local catalog folder    ← named "prompts" when the plugin clones it itself
   Vendor folders/       one directory per vendor, one prompt file per model
   catalog.json          THE LOOKUP TABLE (optional, data-driven)
   personas-pack.md      generated by update-md (never commit to upstream)
        ▼
resolver                pins → resolve cache → alias index → scorer
        ▼
/purge:on → matches the session model → rewrites event.system
```

`update-md` is the maintenance command: it downloads/syncs the catalog, strips
`README.md` from the folder, and regenerates `personas-pack.md` (the whole
folder as one markdown document). `personas-pack.md` is generated output — it
must never be treated as source of truth, and never be edited by hand.

## Commands you will use

| Where | Command | Meaning |
| --- | --- | --- |
| plugin (chat) | `/purge:update-md` | pack the current catalog instantly; if `personaRepoUrl` is set it then syncs in the background and posts a second `update-md: synced:` note (wait for it before diffing the pack; with no URL, the first note is final) |
| plugin (chat) | `/purge:status` | read current resolution (`source: auto (root) N/M — Vendor/file`) |
| plugin (chat) | `/purge:reload` | local rescan only — no network |
| repo | `bun run pack` | same pack as `update-md`, plus the JSON manifest |
| repo | `bun scripts/diag-resolve.ts <root> [provider/id ...] --why` | authoritative resolver probe; exit 1 on misses |

## The lookup table: `<catalog-root>/catalog.json`

Optional file. Absence means built-ins only. User values **append to** the
built-in vocabularies; they never replace or remove them. Keys are lowercase.
Everything is matched case-insensitively.

```jsonc
{
  "modelAliases": {
    "nvidia": ["nemotron", "nemo"],
    "openai": ["gpt-oss"]
  },
  "dirAliases": {
    "raghavraut": ["gemini"],
    "modemnakata": ["nemotron"]
  },
  "generics": ["preview", "latest"],
  "models": {
    "opencode-go/deepseek-v4.1-flash#max": "DeepSeek/deepseek-4-1.md",
    "myprovider/super-model-3": "Stealth Models/spacebunny-agents.md",
    "totally-unknown-id": "OpenAI/gpt-oss-20b.md"
  }
}
```

### Field semantics (exact)

- `modelAliases` — key is a **vendor identity word** (as it appears in vendor
  folder names); values are extra words that should also identify that vendor
  in a provider/model string. Add an alias when the model ref uses a synonym
  but the folder uses the canonical name.
- `dirAliases` — key is the **exact vendor folder name, lowercase**; values are
  identity words the folder itself does not contain (author handles, project
  names). Add when the vendor folder is a handle like `raghavraut` but its
  files belong to a known model family.
- `generics` — words that must **never** count as vendor identity. Extract a
  word out of folders/aliases with this when a common noun causes false matches
  (e.g. a folder literally named "Models").
- `models` — **exact pins**, consulted before any scoring. Key forms, checked
  in this order: `provider/id#variant`, `provider/id`, bare `id`. Value must be
  `Vendor/file.md`, or a bare `file.md` when that filename exists in exactly one
  vendor folder. Use pins for one-off ids that scoring cannot reasonably infer;
  do not spray pins for things an alias fixes.

### Decision rules (in priority order)

1. **Wrong vendor** → prefer `dirAliases` (folder is a handle) or
   `modelAliases` (provider spells the family differently).
2. **Right vendor, wrong file** → prefer **renaming nothing** and pinning via
   `models`, or adding an alias if the file name differs only in wording.
   Never rename vendor folders or prompt files — both are upstream content.
3. **Miss due to a generic word** → add the word to `generics`.
4. **One exact id, likely stable** → single `models` pin.
5. If the catalog has **no prompt for the model family at all**, do not
   fabricate one, do not copy another family's file under a new name, and do
   not pin an unrelated file. Leave it unresolved; the plugin's `fallback`
   governs behavior (default `none` keeps OpenCode's stock prompt).

## Update workflow (do every step)

1. Sync the catalog: run `/purge:update-md` (chat) or `bun run pack`
   (repo, with `PERSONA_REPO` set). The chat command packs instantly and,
   when `personaRepoUrl` is configured, follows up with an
   `update-md: synced:` note after the background pull — wait for that second
   note (or for the single note if no URL is set) before reading the pack.
2. Note the counts. The default catalog today is **19 vendors / 50 files**.
   A change in these numbers is legitimate (upstream moved) but record it.
3. Probe the models in question — never trust intuition:
   `bun scripts/diag-resolve.ts <root> <provider/id ...> --why`
4. Only now edit `catalog.json` with the **minimal** entry from the decision
   rules. Keep it valid JSON; keep keys lowercase; do not add speculative
   entries for models nobody uses.
5. Re-probe: every probed ref must print a `Vendor/file.md`. Then
   `bun run pack` again so `personas-pack.md` reflects the final state
   (the pack honors `catalog.json` only for resolution — the pack always
   contains the whole folder verbatim).
6. Run the test suite: `bun test` (expect ≥ 70 passing, 0 failing with env
   vars set; the host suite is `node scripts/host-test.mjs <opencode-clone>`).
7. Report: root used, counts, before/after resolution per probed model, files
   touched, and any unresolved models with the reason (`no vendor identity
   match` / `version incompatible` / `no such family in catalog`).

## Hard don'ts

- Don't edit `src/catalog.ts` for a single model — that file holds shared
  defaults and tests pin its behavior; use `catalog.json`.
- Don't touch `personas-pack.md` by hand. Regenerate.
- Don't delete vendor folders or prompt files to "clean up".
- Don't commit the upstream catalog into this plugin's repository.
- Don't claim a match from memory; `diag-resolve` is the only accepted
  evidence.

## Failure signatures you will meet

| Symptom | Meaning | Fix |
| --- | --- | --- |
| `NO MATCH`, no vendor lines printed | no identity word overlaps | `modelAliases`; pin as last resort |
| `NO MATCH` + vendor line with negative best-file score | vendor matched, no file plausible | `models` pin to the correct file, or leave unresolved |
| resolves to a different family (e.g. gemini→`Gemini-4-Argon`) | no file carries the model's major version in the chosen folder | check for a folder that actually carries the version; alias it with `dirAliases` |
| resolves to `*-agents` variant instead of the plain file | token-rich name beat the exact name | should not happen since exact squashed names outrank; if it does, report it — do not pin around a resolver bug |
| `/purge:on` says `no persona for … (fallback: none)` | intentional refusal — nothing matched | same fixes as above |

## Where things live

- Plugin source: `src/index.ts` (plugin), `src/catalog.ts` (resolver), `src/pack.ts` (pack), `src/repo.ts` (git sync), `src/sandbox.ts` (permission ceilings).
- Docs: `README.md` (user-facing), this file (agent-facing).
- Generated by `update-md`/`pack`: `personas-pack.md` (catalog root) and, for the repo command, `dist/personas-pack.{json,md}` (git-ignored).
